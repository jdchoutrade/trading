## 1. Executive Summary & Root Cause Analysis

### Why signals entered and hit TPs were not saved in History or tracked
1. **No Automatic Signal Emitter / Persistence Hook:**
   - In the existing codebase, `runFullAnalysisPipeline()` produces a technical analysis snapshot and a `tradePlan` on request (e.g. when `/api/snapshot` or `/api/analyze` is polled/requested), but **does not emit or persist new actionable signals into the database**.
   - Signals were only appended to `store.ts` if a client explicitly called `POST /api/signals`. When the analysis pipeline generated a valid BUY/SELL trade plan, it evaporated after the response was rendered.
2. **Missing Live Outcome Tracker State Machine:**
   - `server/db/store.ts` had a rudimentary `liveTrackers` list, but there was **no live service listening to real-time market ticks/candles** to drive a state machine from `PENDING` → `TRIGGERED` → `TP1_HIT` / `SL_HIT`.
   - As a consequence, once a trade was manually logged or planned, prices moved in the live market without updating the trade lifecycle, calculating R-multiples, or recording exit times.
3. **Database Architecture Limitations:**
   - Previous storage relied purely on `data/db.json` in memory without transactional guarantees, relational integrity, append-only event logs, or hash chains.
   - There was no separation between immutable signal parameters (`entryPrice`, `stopLoss`, `tp1`, `snapshot_hash`) and mutable/derived outcome metrics (`fill_price`, `realizedR`, `mfe`, `mae`).

  - Zero survivorship bias: All signals generated by the system must be logged regardless of user execution or outcome.

## 4. Signal Lifecycle & State Machine Specification

### 4.1 State Machine Diagram
```
PENDING ──(Ask/Bid touches Entry Zone)──▶ TRIGGERED ──▶ TP1_HIT ──▶ (BE Armed) ──▶ TP2_HIT ──▶ TP3_HIT
   │                                           │             │
   │                                           ├──▶ SL_HIT   ├──▶ BE_EXIT / TRAIL_EXIT / SL_AFTER_TP1
   │                                           ├──▶ INVALIDATED (opposite CHoCH/session blackout)
   │                                           └──▶ TIME_STOP (max candles elapsed)
   ├──▶ EXPIRED (limit zone not reached within N bars)
   └──▶ CANCELLED (pre-entry structural invalidation / news shock)
```

### 4.2 Spread-Aware Hit Rules
- **BUY Signals:**
  - Entry Trigger: `Ask <= EntryPrice` (or Ask touches entry zone for limit orders).
  - SL Hit: `Bid <= StopLoss`.
  - TP1/2/3 Hit: `Bid >= TP`.
  - Exit calculation: measured against live `Bid`.
- **SELL Signals:**
  - Entry Trigger: `Bid >= EntryPrice` (or Bid touches entry zone).
  - SL Hit: `Ask >= StopLoss`.
  - TP1/2/3 Hit: `Ask <= TP`.
  - Exit calculation: measured against live `Ask`.

### 4.3 Ambiguous Same-Candle Resolution
- When inspecting historical candle intervals (during backfill or when tick data is unavailable) where both high and low breach TP and SL levels within the same bar:
  - **Conservative Default:** Assume **SL was hit first**.
  - **Audit Flag:** Mark record with `ambiguous_resolved_conservative = 1`.
  - Report the count and percentage of ambiguous outcomes transparently in stats.

### 4.4 Feed Interruption & Stale State Handling
- If data feed latency $> 3000\text{ms}$ or disconnected:
  - Tracker status shifts to `TRACKING PAUSED (stale)`.
  - Signal processing halts without assuming fake prices.
  - When feed re-establishes: Backfill missing candles from TradingView Chart Session, inspect intermediate prices chronologically, and mark any resulting event with `source = 'reconstructed'`.

## 5. SQLite Data Model & Migration Architecture

We implement a versioned SQLite relational schema via `node:sqlite` (`data/gold_desk.db`) ensuring ACID compliance, immutability triggers, and JSON backwards-compatibility:

1. `signals`: Immutable record of every algorithmic recommendation generated.
2. `signal_events`: Append-only transition log (`PENDING`, `TRIGGERED`, `TP1_HIT`, `SL_HIT`, etc.).
3. `signal_outcomes`: Materialized outcome state with $R$-multiples, MFE, MAE, and duration.
4. `my_trades`: Personal execution records linked to signal IDs or discretionary trades.
5. `signal_notes`: User annotations, tags, and execution reflections.
6. `schema_migrations`: Version tracker (`v1_init`, `v2_hash_chain`, etc.).

### SHA-256 Hash Chain
- Each signal snapshot computes:
  $$\text{hash}_i = \text{SHA256}(\text{signal\_id} + \text{created\_ts} + \text{symbol} + \text{direction} + \text{entry} + \text{sl} + \text{tp1} + \text{factors} + \text{hash}_{i-1})$$
- Ensures historical immutability; verifiable via `GET /api/signals/:id/verify` and CLI script `npm run verify:history`.
